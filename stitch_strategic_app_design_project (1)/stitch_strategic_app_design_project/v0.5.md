*"아는 사람만, 아는 식당만" — 폐쇄형 네트워크 기반 단체 예약·모임 운영 자동화*

버전: v0.5

# 1. 개요

## 1.1. 배경

모임(협회, 회사, 사적 네트워크 등)의 총무·재무·사무총장은 정기 회식·모임 자리를 예약하는 데 상당한 반복 업무를 소모하고 있다. 특히 5인 이상 단체 예약은 캐치테이블 등 기존 예약 플랫폼에서 사실상 지원되지 않는다. 개별 식당이 온라인 예약 시스템에 등록할 때 테이블 배치상 4인 이하까지만 슬롯을 열어두고, 대형 인원은 전화 문의로 유도하는 구조적 관행 때문이다.

본 서비스의 출발점은 특정 개인(창업자 본인)이 4개 이상의 모임에서 총무·사무총장을 동시에 맡으며 겪은 실제 관리 부담이다. 여러 모임을 동시에 운영할 때 발생하는 일정·이력·회비의 혼선, 그리고 반복되는 식당 선택이 개인의 사적 판단처럼 비칠 수 있다는 정치적 부담이 핵심 문제로 확인되었다.

*이 서비스의 진짜 문제 정의: "모임을 가입시키는 것"이 아니라, "여러 모임을 동시에 운영하는 총무·재무의 관리 부담을 줄이고, 그의 선택에 시스템적 명분을 부여하는 것"이다.*

## 1.2. 한 줄 정의

**초대·승인 기반으로만 가입 가능한 폐쇄형 네트워크 안에서, 모임(수요)과 식당(공급)을 협력사·협회 등 신뢰 관계로 연결하고, 총무·재무의 반복 업무를 자동화하며, 그 선택에 시스템적 근거와 명분을 부여하는 B2B2C 플랫폼.**

## 1.3. 기존 예약 플랫폼과의 차별점

| **구분**         | **기존 예약 플랫폼 (캐치테이블 등)** | **본 서비스**                            |
|------------------|--------------------------------------|------------------------------------------|
| 접근성           | 누구나 가입, 오픈 검색               | 초대·승인 기반 폐쇄형 회원제             |
| 인원             | 1~4인 중심, 대형 인원은 전화 유도    | 5인 이상 단체 예약이 기본 시나리오       |
| 탐색 방식        | 사용자가 직접 검색 (Pull)            | 조건 기반 선제적 추천 알림 (Push)        |
| 식당 데이터      | 오픈 등록 (누구나 입점)              | 협력사·협회 거래처만 등록 (신뢰 기반)    |
| 핵심 사용자 단위 | 개인                                 | 여러 모임을 동시 운영하는 총무·재무      |
| 핵심 가치        | 빠른 예약 성사                       | 멀티 모임 관리 자동화 + 선택의 명분 제공 |

## 1.4. 공정성 원칙

*"광고 없이, 인원·지역·요청조건에 따라 최적의 5곳을 공정하게 추천합니다." — 특정 업체를 광고비로 밀어주지 않는다는 원칙을 서비스의 핵심 슬로건이자 추천 알고리즘의 설계 기준으로 삼는다.*

이 원칙은 단순한 마케팅 문구가 아니라, 총무의 "명분"(1.1, 9장)이 실제로 성립하기 위한 전제조건이다. 광고비가 순위에 영향을 준다는 의심이 생기는 순간, "시스템이 추천했다"는 총무의 방패는 무너진다.

추천 로직은 블랙박스형 딥러닝이 아니라, 누구에게나 설명 가능한 규칙 기반 스코어링으로 시작한다. "왜 이 식당이 추천되었는지"를 총무·식당 모두에게 항상 설명할 수 있어야 신뢰가 유지된다.

**추천 로직 — 2단계 구조**

| **단계**                  | **내용**                                                                              | **회원사 매장 처리**                               |
|---------------------------|---------------------------------------------------------------------------------------|----------------------------------------------------|
| ① 필터 (절대 공정)        | 수용 인원, 지역 반경, 필수 편의시설 등 조건 미충족 시 후보에서 제외                   | 예외 없음 — 회원사 매장도 동일 기준 미충족 시 제외 |
| ② 정렬 (의도적 가점 허용) | 필터를 통과한 후보 안에서 최근 미방문 여부, 예산 적합도, 식당 신뢰도 등으로 순위 결정 | "회원사 운영" 태그 부여 및 우선순위 가점 적용      |

| **구분**       | **항목**                                                                          | **순위 반영 여부**                  |
|----------------|-----------------------------------------------------------------------------------|-------------------------------------|
| 필수 조건      | 수용 인원 · 지역 반경 · 필수 편의시설                                             | 미충족 시 후보에서 원천 제외        |
| 가점 요소      | 최근 미방문 여부 · 예산 적합도 · 식당 신뢰도(노쇼·성사율) · 회원사 운영 매장 여부 | 필터 통과 후보 안에서만 점수화·정렬 |
| 절대 배제 요소 | 광고비 지불 여부 · 협력사와의 관계 친밀도 · 혜택 규모(Phase 2 보류 항목)          | 순위에 절대 반영하지 않음           |

회원사 운영 매장 우선 노출은 형평성 원칙의 유일한 의도적 가점이다. 다만 이는 조건 필터를 통과한 후보 사이에서만 작동하며, "회원사 운영" 태그를 후보 카드에 명시적으로 노출하여 총무가 우선순위의 이유를 항상 확인할 수 있게 한다. 숨겨진 가점이 아니라 보이는 가점으로 운영하는 것이 원칙이다.

# 2. 문제 정의 — 실사용 시나리오

본 서비스의 요구사항은 실제 사무총장 업무 사례에서 도출되었다.

- 매달 둘째주 화요일 저녁 6시, 고양시 일산 백석역·서구 인근에서 10~12명 회식 자리를 잡아야 함

- 조건: 주차장 필수, 최근 3개월 이내 방문하지 않은 메뉴여야 함

- 협력사(예: 롯데칠성음료) 영업사원에게 매달 납품처 중 4~5곳 추천을 요청, 총무가 선택하면 영업사원이 대신 예약

- 확정된 식당 기준 공지 작성 → 단체 대화방 게시 → 미응답자 일일이 전화 확인

- 이 과정을 동시에 4개 이상의 모임에서 반복 — 모임 간 일정·이력·회비가 뒤섞이는 관리 부담 발생

- 같은 식당을 반복 추천하면 "총무 개인이 뭔가 받는 것 아니냐"는 의심을 살 수 있는 정치적 리스크 존재

*본 서비스는 이 반복 업무의 자동화와, 총무의 선택에 대한 시스템적 정당성 부여를 동시에 해결하는 것을 목표로 한다.*

# 3. 핵심 사용자 정의

## 3.1. 1차 페르소나 — 멀티 모임 총무·재무

본 서비스의 실질적 성장 동력은 "모임 단위 영업"이 아니라 "여러 모임에서 총무·재무를 겸직하는 특정 인물군"의 확보다. 이런 인물 한 명을 확보하면, 그가 관여하는 모임 3~5개가 함께 유입되는 구조적 특성이 있다.

- 초기 파일럿 타겟: 협회 임원, 여러 동문회·조기축구회 등을 동시에 운영해본 경험이 있는 인물

- 이들이 모이는 상위 네트워크(협회 임원 모임, 동문회 연합 등)가 개별 식당·협력사 영업보다 효율적인 확보 채널

## 3.2. 3계층 네트워크 구조

| **계층**             | **구성원 예시**                                            | **역할**                                                          |
|----------------------|------------------------------------------------------------|-------------------------------------------------------------------|
| ① 모임 (수요)        | 협회, 회사 모임, 사적 네트워크의 총무·재무·사무총장        | 정기/비정기 모임 조건 등록, 예약 요청·확정                        |
| ② 식당 (공급)        | 협력사 거래처, 협회 회원사 식당, 회원이 직접 운영하는 매장 | 특정 협력사·협회·모임 경로로만 노출·예약 가능                     |

# 4. 핵심 기능 (MVP 범위)

## 4.1. 모임 프로필 및 반복 스케줄

- 모임 고정 조건: 인원수, 선호 지역, 예산대, 필수 편의시설(주차장 등)

- 반복 일정 등록 (예: 매월 둘째 주 화요일 18:00)

- 모임 단위 방문 이력 자동 축적 → 최근 90일 방문 메뉴·식당 자동 제외 필터

## 4.2. 선제적 추천 알림 및 추천 근거 표시

- D-14, D-7 시점, 조건에 맞는 식당 3~5곳 자동 추천 (정기 모임은 연결자가 큐레이션)

- 추천 로직은 1.4절 공정성 원칙의 2단계(필터 → 정렬) 구조를 그대로 따름 — 광고비·협력사 친밀도는 순위에 절대 미반영

- 추천 카드에 매칭 근거를 명시 (예: "최근 3개월 미방문 · 주차 가능 · 10~12인 수용", 회원사 매장인 경우 "회원사 운영" 태그 추가 표시)

- 이 근거 표시는 공지 공유 시에도 함께 노출되어, 총무의 선택이 개인 취향이 아닌 시스템 판단으로 인지되도록 함

- 비정기·소수 인원 모임은 연결자를 통한 프라이빗 예약(우대예약) 지원 — 확정 카드에 "OOO님이 특별히 챙긴 우대예약" 형태로 표시

## 4.3. 예약 요청 및 대행

- 총무가 추천 후보 중 선택 → 연결자에게 예약 요청 전송 → 연결자가 식당과 확정

- 확정 상태를 총무가 앱에서 실시간 확인

## 4.4. 자동 공지 및 출결 관리

- 예약 확정 시 날짜·장소·주차정보·메뉴 요약을 담은 공지문을 자동 생성, "복사하기" 버튼으로 클립보드에 즉시 담아 카톡 등 외부 채널에 붙여넣기 가능

- 공지 복사 후에는 "복귀 확인" 버튼을 총무가 직접 눌러야 다음 단계(참석현황 화면)로 진행 — 외부 앱 이동 중 붙여넣기 실패 등의 문제를 총무가 인지한 상태에서 넘어가도록 자동 전환을 배제함

- 참석 여부 투표 및 미응답자 자동 리마인드 — 최종 미응답자만 총무에게 리스트업

- 예약일 익일(T+1), 참석 확인 데이터를 기반으로 재무보고를 자동 생성 — 세부 항목(회비 배분 방식 등)은 재무 업무 담당자와 협의하여 추후 구체화, MVP에서는 "생성 여부와 시점"만 확정

## 4.5. 멀티 모임 허브

한 사람이 여러 모임의 총무·재무를 동시에 맡는 경우를 기본 시나리오로 설계한다.

- 로그인 시 본인이 관리하는 모든 모임을 한 화면에 리스트로 표시, 모임 간 전환은 원클릭

- 모임 간 일정 충돌 자동 감지 (같은 날짜에 두 모임 예약 진행 방지)

- 모임별 방문 이력·회비 데이터는 철저히 분리 보관 (혼동 방지)

- 신규 가입 온보딩 시 "다른 모임도 관리하고 계신가요?" 질문으로 추가 모임 등록 유도

## 4.6. 총무 개인 성과 프로필

모임 계정과 별개로, 총무 개인에게 귀속되는 성과 자산을 제공한다. 임기가 끝나도 총무 개인의 이력으로 남는다.

- 관리 중인 전체 모임을 합산한 실적 지표: 예약 성사 횟수, 평균 참석률, 노쇼 없는 연속 기록

- 모임원이 남기는 간단 만족도(별점) 누적

- 공지 공유 시 "총무 OOO님이 이번 달에도 예약을 완료했습니다" 형태로 자동 노출 → 총무의 인정 욕구 충족 및 자연스러운 입소문 유발

## 4.7. 회원사 매장 상호소비 지원

모임 회원이 직접 식당을 운영하는 경우, 부담 없이 서로를 챙기는 문화를 시스템으로 지원한다.

- 회원 프로필에 "운영 매장" 선택적 등록 필드 제공

- 우선 노출은 조건 필터(인원·지역·편의시설 등)를 통과한 후보에 한해서만 적용 — 조건 미충족 시 회원사 매장이어도 노출되지 않음 (1.4절 공정성 원칙 준수)

- 필터를 통과한 후보 중에서는 "회원사 운영" 태그와 함께 우선순위 가점 적용, 최종 선택은 총무 자율

- 개인별 이용 여부는 추적·노출하지 않음. 모임 단위 "올해 회원사 매장 이용 횟수"만 연말 리포트에 집계 항목으로 포함

## 4.8. 가입 구조 — 신청서 + 심사 방식

- 최초 진입은 초대코드가 아닌 "가입 신청서" 작성 방식 — 모임명·대략적 인원대·활동지역 등 3~4개 항목만 가볍게 입력하여 진입장벽을 낮춤

- 신청서의 "소개 경로" 응답에 따라 해당 연결자(영업사원)·협회 담당자에게 심사가 자동 위임되며, 소개 경로가 없는 경우 운영자에게 폴백

- 승인 이후에만 상세 조건(예산·필수 편의시설·반복일정 등)을 입력 — 미승인 상태에서 상세 정보를 요구하지 않아 불필요한 이탈을 방지

- 모임 내부 회원 초대, 협력사 소속 영업사원 계정 발급 등 이미 신뢰관계가 확립된 하위 초대는 기존과 동일하게 초대코드 기반으로 유지 (5.2절 위임형 모델과 연동)

- 일반 사용자는 검색으로 서비스를 발견해 자유 가입할 수 없음 — 신청서 접수 자체는 열려 있으나 승인 전까지는 폐쇄형 원칙 유지

# 5. 권한 및 역할 구조

## 5.1. 모임 내부 4역할 체계

| **역할**      | **권한**                                  | **핵심 가치**                                 |
|---------------|-------------------------------------------|-----------------------------------------------|
| 총무          | 예약 진행, 후보 선택, 공지 발송           | 반복 업무 자동화, 개인 성과 프로필            |
| 재무          | 결제 내역 조회, 회비 보고서 열람/다운로드 | 회비 정산 업무 자동화                         |
| 회장 (옵저버) | 조회 전용, 운영 개입 없음                 | 자동 월간/분기 리포트 수신 — 조직 투명성 확보 |
| 일반 모임원   | 참석 여부 응답만                          | 공지 확인, 참석 체크                          |

총무·재무 2인 관리 체계를 기본으로 권장한다. 총무 유고 시에도 모임 운영이 끊기지 않도록 하는 연속성 확보 장치이며, 재무의 회비 보고 업무 부담도 함께 줄여준다.

## 5.2. 네트워크 승인 권한 — 위임형 모델

서비스 운영자가 모든 가입·승인을 직접 처리하지 않도록, 승인 권한을 계층별 보증인(Sponsor)에게 위임한다.

| **권한 주체**     | **위임받는 권한**                                    | **운영자 개입 시점**              |
|-------------------|------------------------------------------------------|-----------------------------------|
| 협력사 관리자     | 소속 영업사원 계정 발급·관리                         | 신규 협력사 최초 등록 시에만      |
| 영업사원 (연결자) | 담당 거래처 식당 초대(등록 대행 아님), 추천 큐레이션 | 신뢰 점수 이상 징후 발생 시에만   |
| 모임 대표/총무    | 소속 모임원 초대·관리                                | 신규 협회/모임군 최초 등록 시에만 |

- 예약 성사율, 노쇼율, 모임 만족도를 자동 축적하여 일정 기준 이하 시 추천 후보에서 자동 제외 (수동 퇴출 불필요)

# 6. 총무 인계 및 계정 연속성 정책

총무는 임기제로 운영되는 경우가 대부분이므로, 계정의 소유 주체를 총무 개인이 아닌 "모임"으로 설계한다.

| **구분**                               | **소유 주체** | **총무 교체 시**                 |
|----------------------------------------|---------------|----------------------------------|
| 모임 프로필, 방문 이력, 신뢰도, 포인트 | 모임 계정     | 그대로 유지                      |
| 로그인 계정(개인 인증)                 | 총무 개인     | 신규 총무로 전환                 |
| 개인 성과 프로필                       | 총무 개인     | 총무 개인에게 귀속되어 계속 유지 |

## 6.1. 인계 프로세스

- 모임 생성 시 총무 임기 필드 등록, 임기 종료 3~4주 전 인계 절차 자동 알림

- 현 총무가 "인계하기" → 후임자 전용 초대 코드 발급 → 코드 입력 시 총무 권한 자동 이양

- 인계 완료 후 신규 총무 계정으로 로그인 전환, 별도 결제수단 등록은 불필요 (v0.4: 결제 주체가 식당으로 이전됨, 7장 참조)

- 신·구 총무 동시 접근 가능한 과도기(예: 2주) 설정으로 인수인계 부실 방지

# 7. 결제 및 정산 정책

*최종 결정: 모임(총무)은 결제를 전혀 하지 않는다. 플랫폼 이용에 대한 비용은 식당이 '유지관리비' 명목으로 인당 정액 부담하며, 예약일 익일 자동결제로 즉시 정산한다.*

## 7.1. 설계 원칙 — 두 문제의 분리

이전 설계(v0.3 이전)는 "노쇼 방지"와 "플랫폼 수익 확보"라는 서로 다른 두 문제를 하나의 예약금 구조에 결합하여, 제3자 정산(지급대행) 라이선스 이슈와 수수료 부담 주체 문제가 얽혀 있었다. v0.4에서는 이를 분리한다.

| **문제**         | **관련 당사자**   | **MVP 처리 방식**                                                                                |
|------------------|-------------------|--------------------------------------------------------------------------------------------------|
| 플랫폼 수익 확보 | 플랫폼 ↔ 식당     | 인당 정액 유지관리비, 식당이 부담 (본 장의 핵심 내용)                                            |
| 노쇼 방지        | 모임(총무) ↔ 식당 | MVP 범위에서는 앱이 직접 관여하지 않음 — 필요 시 Phase 2에서 식당 선택적 옵션으로 재도입 (7.5절) |

이 분리의 핵심 이점은, 플랫폼이 모임의 결제대금을 식당에게 전달하는 제3자 정산(지급대행) 구조를 MVP에서 배제할 수 있다는 것이다. 플랫폼이 식당으로부터 직접 자신의 서비스 이용료를 받는 구조는 일반 가맹점 결제이며, 지급대행 라이선스가 필요한 마켓플레이스 정산과는 규제상 성격이 다르다. 이를 통해 개발 범위와 컴플라이언스 부담을 크게 줄인다.

## 7.2. 요금 구조

| **항목**        | **금액**            | **비고**                                                |
|-----------------|---------------------|---------------------------------------------------------|
| 인당 유지관리비 | 1,000원 / 인        | 식당이 부담. 모임(총무)은 결제 없음, 카드 등록 불필요   |
| 청구 단위       | 예약 1건 = 결제 1건 | 인원별로 쪼개어 청구하지 않음 — PG 최저수수료 손실 방지 |

식당은 손님을 유치하고 실제 매출(식대, 주류 등)을 얻는 대가로 인당 정액을 부담하는 구조이며, 이는 매출 연동형(%) 수수료가 아니라 정액 유치비 성격이다. 부가 매출에 대한 % 수수료는 여전히 부과하지 않는다는 원칙(9장)과 상충하지 않는다.

## 7.3. 자동결제(빌링키) 흐름

| **단계**                     | **내용**                                                                                                     |
|------------------------------|--------------------------------------------------------------------------------------------------------------|
| ① 최초 가입 시 (1회)         | 식당 등록 시 카드 또는 계좌를 빌링키로 등록 — 이후 결제 시 별도 조작 불필요                                  |
| ② 예약 확정                  | 총무가 후보 선택, 연결자가 식당과 확정 — 이 시점에는 결제 발생하지 않음                                      |
| ③ 예약일 익일 (T+1) 자동청구 | 확정 인원 × 1,000원을 예약 1건 단위로 자동 청구. 결제와 동시에 카드 매출전표(영수증) 자동 발급               |
| ④ 알림                       | 카카오 알림톡으로만 통보 (예: "OO모임 10명 예약, 유지관리비 10,000원 자동결제 완료") — 앱 접속 요구하지 않음 |

확정 시점이 아닌 예약일 익일(T+1)을 청구 시점으로 정한 이유는, 월 단위 정산 대비 회수 속도가 빠르면서도, 확정 즉시 청구 시 발생할 수 있는 취소·환불 처리 부담을 피할 수 있기 때문이다. 예약일까지 취소되지 않았다면 사실상 서비스가 이행된 것으로 간주한다.

## 7.4. 증빙 처리

신용카드 결제는 그 자체로 부가가치세법상 적격 증빙(카드 매출전표)이 된다. 결제 시 자동 발급되는 매출전표가 식당의 매입 비용 처리 증빙을 겸하므로, 플랫폼이 별도로 세금계산서를 발행할 필요는 원칙적으로 없다. 앱 내 "결제 내역" 페이지에서 월별 매출전표를 조회·다운로드할 수 있도록 제공한다.

*단, 계좌이체 결제나 특정 거래 형태에서는 증빙 처리 방식이 다를 수 있으므로, 서비스 오픈 전 세무사 확인을 거칠 것을 권장한다.*

## 7.5. 결제 실패 및 미납 처리

- 1차 실패 시 익일 1회 자동 재시도 + 알림톡 발송

- 재실패 시 결제수단 재등록 요청 알림과 함께 유예기간(예: 7일) 부여

- 유예기간 내 미해결 시 다음 추천 후보 풀에서 자동 제외 — 별도의 강제 징수 절차 없이, 노출 중단 자체가 가장 강력한 지렛대로 작동

## 7.6. PG사 선정

창업자가 토스페이먼츠 파트너사 지위를 보유하고 있어, 토스페이먼츠 자동결제(빌링키) 연동을 우선 검토한다. 본 구조는 식당을 대상으로 한 일반 가맹점 결제이므로 별도의 지급대행 라이선스 확인 없이 표준 계약으로 진행 가능할 것으로 예상되나, 계약 전 토스페이먼츠 측에 정확한 상품 구조를 확인할 것을 권장한다.

## 7.7. Phase 2 — 선택적 노쇼 예약금 (보류 기능)

특정 식당이 노쇼 방지를 위한 예약금을 원할 경우, 해당 식당에 한해 모임(총무) 대상 예약금 결제 기능을 선택적으로 활성화하는 것을 향후 확장 옵션으로 남겨둔다. 이 경우 모임의 결제대금이 식당에게 전달되는 제3자 정산 구조가 되므로, 지급대행 라이선스를 갖춘 PG 연동과 법률 검토가 별도로 필요하다. MVP 단계에서는 이 기능을 구현하지 않는다.

| 3차      | 식당 유지관리비       | 인당 1,000원 정액, 식당 부담, 예약일 익일 자동결제 | 손님 유치 대가 — 매출 연동(%) 아님, 모임은 결제 없음 |

## 8.2. 유지관리비 목표치 계산

유지관리비만으로 월 100만원 매출을 목표로 할 경우 (부담 주체가 모임에서 식당으로 바뀌었을 뿐 계산 방식은 동일):

| **평균 모임 인원** | **월 100만원 달성에 필요한 모임 수** |
|--------------------|--------------------------------------|
| 8명                | 월 125건                             |
| 10명               | 월 100건                             |
| 11명               | 월 91건                              |
| 12명               | 월 83건                              |

평균 10명 모임 기준, 100개 모임(식당 기준으로는 월 100건의 예약 성사)을 확보하면 월 100만원이 기본값이 된다. PG 결제가 인당 1,000원(소액) 단위로만 발생하므로 PG 수수료 부담이 작아 순마진은 약 97% 수준으로 추정된다 (7.2절 요금구조 기준). 다만 이는 연 매출 약 1,200만원 규모로 단독 사업성은 크지 않으므로, 1·2차 수익원(B2B 구독료·협회 라이선스)과 함께 설계해야 한다.

*성장 전략의 핵심: "모임 100개를 개별 영업"하는 것이 아니라, 여러 모임의 총무·재무를 겸직하는 인물 20~30명을 확보하면 그가 관여하는 모임이 함께 유입되는 구조를 활용한다.*

# 9. 확산 전략 — 명분 기반 협회 파트너십

본 서비스의 확산은 세 주체 각각에게 "명분"을 제공하는 구조로 설계한다.

| **대상**         | **제공되는 명분**                                                                      |
|------------------|----------------------------------------------------------------------------------------|
| 총무             | "제가 고른 게 아니라 시스템이 추천했습니다" — 개인 선택에 대한 정치적 부담 해소        |
| 식당             | "협회 인증을 받은 골목상권 활성화 채널" — 수수료 없는 손님 유입 채널이자 인증된 자긍심 |
| 협회 임원/공무원 | "이 앱 사용이 곧 소상공인 지원 실적" — 개인 성과(KPI)로 연결되어 자발적 홍보 유인 발생 |

## 9.1. 구체 기능

- 인증 식당 배지: 외식업중앙회/소상공인연합회 명의 인증 마크 부여 — 온보딩 저항 완화

- 지역경제 기여도 리포트: "OO협회 회원들이 올해 골목상권에 총 X천만원 소비" — 협회장의 임기 성과 보고 자료로 활용 가능

- 임원 앰버서더 프로그램: 지부장·임원의 확산 실적을 트래킹하여 조직 단위 기여도로 재활용

## 9.2. 초기 파일럿 채널

창업자가 현재 보유한 고양시 소상공인연합회 홍보이사 직함을 1호 파일럿 채널로 활용 가능. 별도 협력사 영업 없이 "인증 식당 + 총무 명분 + 협회 성과 리포트" 조합을 즉시 검증할 수 있는 위치에 있다.

## 9.3. 검토 필요 사항

*관공서·공무원 회식으로의 확산은 파급력이 크지만, 예산 집행 규정 및 청탁금지법(부정청탁 및 금품등 수수의 금지에 관한 법률) 관련 이슈가 얽혀 있을 수 있다. "권장 채널"로 포지셔닝하고 강제성을 배제하며, 실제 확산 전 관련 법률 검토를 권장한다.*

# 11. 리스크 및 검토 필요 사항

- 결제 구조는 v0.4에서 식당 대상 일반 가맹점 결제로 단순화되어 지급대행 규제 부담이 크게 줄었으나, PG사(토스페이먼츠)와의 계약 전 상품 구조 확인 필요 (7.6절), 카드 매출전표의 세무 증빙 처리도 세무사 확인 권장 (7.4절)

- Phase 2에서 노쇼 예약금(모임 대상)을 재도입할 경우, 그 시점에 제3자 정산(지급대행) 관련 법률 검토가 다시 필요함 (7.7절)

- 관공서 대상 확산 시 예산·청탁금지법 관련 검토 — 9.3절 참조

- 추천 순위의 공정성 — 광고비·혜택 규모가 노출 순위에 영향을 주지 않도록 원칙(1.4절) 유지 필요, Phase 2 혜택 경쟁 기능 도입 시에도 이 원칙과 충돌하지 않게 설계 (10장 참조)

- 초기 콜드스타트: 연결자(영업사원 등) 역할을 할 파트너 확보 속도가 초기 성패를 좌우

# 12. 사용자 경험 흐름 (UX Flow)

4개 역할(총무·식당·연결자·관리자)이 실제로 겪는 화면 단위 흐름을 정리한다. 각 흐름은 지금까지 정의한 기능·정책(4장 핵심기능, 5장 권한구조, 7장 결제정책)을 화면 순서로 재구성한 것이다.

## 12.1. 총무 — 가입부터 인계까지

**가입 및 온보딩**

| **단계**                | **내용**                                                     |
|-------------------------|--------------------------------------------------------------|
| ① 가입 신청서 작성      | 모임명·인원대·지역 등 간단히 (4.8절)                         |
| ② 심사 대기             | 소개 경로에 따라 연결자·협회에 자동 위임, 없으면 운영자 폴백 |
| ③ 승인 알림 수신        | 거절 시 사유 안내 및 재신청 경로 제공                        |
| ④ 개인 정보 등록        | 이름·연락처·역할, 다른 모임 관리 여부 확인(멀티모임 유도)    |
| ⑤ 모임 프로필 상세 등록 | 인원·지역 필수, 예산·편의시설은 선택 입력                    |
| ⑥ 반복 일정 등록        | 비정기 모임은 건너뛰기 가능                                  |
| ⑦ 재무 초대 (선택)      | 2인 관리체계 권장, 나중에 마이페이지에서도 가능              |

**핵심 반복 사이클 — 홈에서 시작**

| **단계**                | **내용**                                                            |
|-------------------------|---------------------------------------------------------------------|
| 홈 (멀티모임 허브)      | 관리 중인 모임 탭 전환, 처리할 일 요약, 개인 성과·재무보고 바로가기 |
| 추천 알림 → 후보 확인   | D-14/D-7 자동 알림, 근거·회원사 태그 표시된 3~5곳                   |
| 후보 선택 → 예약 요청   | 연결자에게 전송, 연결자 확정 후 알림 수신                           |
| 공지문 확인 → 복사      | 장소·시간·주차 요약, 클립보드 복사                                  |
| 카톡 붙여넣기 (앱 외부) | 복귀 후 "복귀 확인" 버튼을 직접 클릭해야 다음 단계 진행             |
| 참석현황 집계           | 회원별 응답 실시간 확인, 마감 후 미응답자만 리스트업                |
| 익일 재무보고 확인      | T+1 자동 생성, 홈으로 복귀하며 다음 사이클 반복                     |

**총무 인계**

| **단계**         | **내용**                                                           |
|------------------|--------------------------------------------------------------------|
| 임기 종료 알림   | 종료 3~4주 전 자동발송                                             |
| 인계하기 실행    | 현 총무가 직접 후임자 코드 발급                                    |
| 후임자 코드 입력 | 권한 이양, 신규 총무 계정 활성화                                   |
| 과도기 2주       | 신·구 총무 동시 접근 가능                                          |
| 구총무 접근 종료 | 신총무 단독 관리 시작 (모임의 이력·데이터는 그대로 유지, 6장 참조) |

**예외 처리**

| **상황**                   | **처리 방식**                                                 |
|----------------------------|---------------------------------------------------------------|
| 추천 후보 전부 불만족      | "다른 후보 요청" → 연결자에게 재요청 알림 → 1~2일 내 재수신   |
| 가입 심사 거절             | 거절 사유 표시 + 재신청 경로 안내                             |
| 비정기 모임(반복일정 없음) | 홈 화면에 "새 모임 예약 요청하기" 버튼 상시 노출, 수동 트리거 |

## 12.2. 식당 — 등록부터 자동결제까지

| **단계**                   | **내용**                                  |
|----------------------------|-------------------------------------------|
| ① 등록 신청                | 연결자 추천 또는 사장님 직접 신청         |
| ② 심사 대기                | 연결자·협회 확인                          |
| ③ 매장 정보 입력           | 수용인원·주차·지역 등 추천 필터 기준 정보 |
| ④ 빌링키 등록              | 자동결제용 카드·계좌, 최초 1회만          |
| ⑤ 인증 배지 부여           | 추천 후보 노출 시작                       |
| ⑥ 예약 확정 알림 수신      | 카카오 알림톡, 앱 접속 불필요             |
| ⑦ 예약일 익일 자동결제     | 확정 인원 × 1,000원, 예약 1건 단위로 청구 |
| ⑧ 매출전표 발급, 완료 알림 | 결제와 동시에 증빙 자동 완결 (7.4절)      |
| ⑨ 결제 내역 조회 (선택)    | 필요할 때만 앱 접속                       |

식당 사장님의 정상 경로는 ①~⑤ 최초 가입 이후 ⑥~⑧이 알림톡만으로 반복되는 것이며, 앱에 재접속할 필요가 없도록 설계하는 것이 원칙이다 (7장 설계 원칙과 연동).

**예외 처리**

| **상황**                | **처리 방식**                                                                    |
|-------------------------|----------------------------------------------------------------------------------|
| 예약이 예약일 전 취소됨 | 익일 자동결제 자체가 실행되지 않음, 별도 알림 없음                               |
| 자동결제 실패           | 익일 1회 재시도 + 알림톡 → 재실패 시 유예기간(7일) → 미해결 시 노출 중단 (7.5절) |
| 가입 심사 거절          | 거절 사유 안내 + 재신청 경로 제공                                                |

## 12.3. 연결자 — 온보딩부터 예약확정 처리까지

| **단계**                  | **내용**                                                  |
|---------------------------|-----------------------------------------------------------|
| ① 협력사 관리자 초대 수신 | 계정 활성화, 별도 승인 절차 없음 (위임형 모델)            |
| ② 거래처 식당 초대 발송   | 링크 공유, 등록·빌링키 입력은 식당이 직접 (12.2절과 연동) |
| ③ 등록완료 식당 자동 연동 | 담당 거래처 풀에 편입                                     |
| ④ 추천 요청 알림 수신     | 정기 D-14/D-7 또는 프라이빗 소수인원 요청                 |
| ⑤ 후보 큐레이션           | 조건 맞는 3~5곳 선택, 총무에게 전송                       |
| ⑥ 식당과 예약 확정 처리   | 전화·카톡 등 오프라인 채널 병행 가능                      |
| ⑦ 확정 상태 입력          | 총무·식당에 자동 알림 발송                                |

**예외 처리**

| **상황**                  | **처리 방식**                                              |
|---------------------------|------------------------------------------------------------|
| 초대한 식당이 가입 미완료 | 7일 후 리마인드, 이후 초대 목록에서 만료 표시(재발송 가능) |
| 큐레이션 마감 시한 초과   | 총무·연결자 양측에 지연 알림 자동 발송                     |

## 12.4. 관리자 (운영자) — 감시와 최초 온보딩 중심

운영자는 일상 업무 화면을 갖지 않는다. 위임형 모델(5.2절)이 정상 작동하는 한, 대시보드는 예외 감시와 신규 최상위 파트너 온보딩 두 가지 목적으로만 쓰인다.

| **영역**      | **내용**                                                      |
|---------------|---------------------------------------------------------------|
| 상단 요약     | 전체 모임 수·식당 수·이번 달 유지관리비 매출·목표 대비 진행률 |
| 심사 대기함   | 연결자 폴백 건만 도달 — 쌓여 있다면 위임 구조 점검 신호       |
| 이상징후 알림 | 결제 미납, 신뢰점수 급락, 인계 분쟁 등                        |
| 파트너 관리   | 협력사·협회 목록, 신규 온보딩 시작                            |
| 확산 현황     | 인증배지 발급 수, 협회별 지역경제 기여 리포트 현황(9장)       |

**신규 파트너 온보딩 (운영자 직접 개입의 유일한 정기 업무)**

| **단계**                | **내용**                                 |
|-------------------------|------------------------------------------|
| ① 신규 파트너 접촉      | 오프라인 미팅, 앱 밖에서 진행            |
| ② 파트너 계정 최초 생성 | 운영자가 직접 실행                       |
| ③ 관리자 권한 부여      | 협력사·협회 담당자에게                   |
| ④ 위임 구조로 이관      | 이후 연결자 자율 온보딩(12.3절)으로 전환 |

**이상징후 대응**

| **단계**             | **내용**                       |
|----------------------|--------------------------------|
| ① 이상징후 알림 수신 | 미납·신뢰점수 급락 등 자동감지 |
| ② 케이스 검토        | 상세 이력·로그 확인            |
| ③ 조치 결정          | 경고·노출제외·계정정지         |
| ④ 조치 반영          | 당사자 자동 알림               |
